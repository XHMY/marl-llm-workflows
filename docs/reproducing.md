# Reproducing the experiments

The experiment grid is workflow x policy x scale x task:

- Workflows: Voting (`voting`), Evaluator-Optimizer (`evaluator_optimizer`), Orchestrator-Workers
  (`orchestrator_workers_propose`), and the single-agent RL baseline (`single_agent`, SA-RL).
- Policies: `ip` (one LoRA adapter per role) and `sp` (one adapter shared by all roles). SA-RL has one
  role and runs as `ip` only.
- Scales: Qwen3-0.6B, Qwen3-1.7B, Qwen3-4B.
- Tasks: Math (DAPO-Math-17K) and Code (DeepCoder, PrimeIntellect subset).

That is 36 multi-agent cells plus 6 SA-RL runs, and a set of controls on the 1.7B Math cells.
Every run is launched with `scripts/launch.py`. The launcher prints the Hydra command of the trainer
(`--print`), renders a SLURM script (`--slurm-config`), or submits it (`--submit`).

## 1. Prepare the data

```bash
source scripts/env.sh                      # or use the editable installs (installation.md)
export MARL_DATA_DIR=$PWD/data_cache       # dataset registry root
python -m marl_workflows.data.prepare_dapo_math --verify   # Math train set + 1412-problem validation split
python -m marl_workflows.data.prepare_aime --verify        # AIME 2025 (in-training validation) and AIME 2024
python -m marl_workflows.data.prepare_math500 --verify     # optional independent test set
python -m marl_workflows.data.prepare_deepcoder --verify   # Code train set + 1000-problem validation split
```

`--verify` checks row counts and content hashes against `marl_workflows/data/checksums.json`.

## 2. Launch a cell

```bash
# print the command
python scripts/launch.py --task math --workflow voting --policy ip --scale 1.7B --print
# render the SLURM script, then submit it as three chained segments that resume from each other
python scripts/launch.py --task math --workflow voting --policy ip --scale 1.7B \
    --slurm-config configs/slurm/dgxh_preempt_h100.conf
python scripts/launch.py --task math --workflow voting --policy ip --scale 1.7B \
    --slurm-config configs/slurm/dgxh_preempt_h100.conf --time 0-05:50:00 --submit --chain 3
```

A cell's defaults (role names, prompt and response caps, workflow parameters, per-GPU token budget)
come from `marl_workflows/recipes.py` and `marl_workflows/launch.py`; see
[configuration.md](configuration.md). The per-GPU token budget depends on the GPU type
(`--gpu-type`, or the `GPU_TYPE` line of the SLURM conf). Code jobs size the code-execution pool to
the allocated CPUs (16 per GPU by default).

GPU guidance: train 4B on 80 GB GPUs (H100 or H200) only; 0.6B and 1.7B also fit 48 GB L40S pairs.
The launcher refuses other combinations when it renders a SLURM script (`--skip-gpu-check` overrides).

Restarting a run: launching the same command again resumes from the latest checkpoint in
`checkpoints/<project>/<experiment>/`. A finished run prints `RUN_COMPLETE global_step=N` and exits 0,
so extra chained segments are harmless. With `--chain K` the launcher also enables the trainer's
wall-clock stop, which saves a checkpoint before the SLURM time limit.

## 3. Reproduce a paper run exactly

`configs/paper_runs.yaml` records, for each of the 52 paper runs (42 grid runs and 10 controls), the
launcher inputs that reproduce it:

```bash
python scripts/launch.py --paper-run lm7qcvrf --print
python scripts/launch.py --paper-run lm7qcvrf --slurm-config configs/slurm/dgxh_preempt_h100.conf --submit --chain 4
```

`--paper-run` pins the experiment name, the wandb project of the paper runs
(`rllm-workflow-MARL-v2`), the number of GPUs, the per-GPU token budget, the code-execution pool size
(the rendered SLURM job allocates at least one CPU per pool worker, as the original runs did), the
number of training steps and the learning-rate warmup, plus any run-specific overrides. The values
come from the logged configs of the original runs; the warmup comes from the logged learning-rate
series (15 steps of linear warmup, or none), because the logged config of a resumed run can show a
warmup the run never took. `tests/test_paper_runs.py` checks that the generated command equals the
logged config on every key it sets.

Differences that a reproduction cannot remove are recorded in each entry's `notes`:

- Some runs were resumed from an earlier run (`resumed_from`); a fresh launch trains the whole run in
  one go.
- One Code run used a per-test code executor that this package does not include; the reproduction
  uses the process pool.
- Two SA-RL runs were logged under older experiment names (`logged_experiment_name`); the reproduction
  uses the standard name so that evaluation finds the checkpoints.

`configs/paper_runs.yaml` is generated by `scripts/export_paper_runs.py` from the original wandb
records and is not edited by hand.

### Controls

A control is applied on top of a base cell with `--control`. The table lists the base cell used in the
paper; any compatible cell works.

| Control | What changes | Launcher arguments | Paper run |
|---|---|---|---|
| `per_voter_reward` | Each voter is rewarded for its own answer instead of the episode outcome. | `--task math --workflow voting --policy ip --scale 1.7B --control per_voter_reward` | `--paper-run lottt3pm` |
| `evaluator_accuracy_reward` | Each role is rewarded for its own correctness instead of the episode outcome. | `--task math --workflow evaluator_optimizer --policy ip --scale 1.7B --control evaluator_accuracy_reward` | `--paper-run nsn0gxle` |
| `prompt_het` | Voting with a different prompt per voter (workflow voting_prompt_het). | `--task math --workflow voting_prompt_het --policy ip --scale 1.7B --control prompt_het` | `--paper-run 5u3lopo4` |
| `single_role` | Three independent generator samples per problem on one adapter, no aggregator. | `--task math --workflow controlled_sa_hga --policy ip --scale 1.7B --control single_role` | `--paper-run 2nxiq4fy` |
| `voter_adapters_rubric` | One adapter per voter (workflow voting_v2), each voter rewarded by a rubric. | `--task math --workflow voting_v2 --policy ip --scale 1.7B --control voter_adapters_rubric` | `--paper-run uftb3s45` |
| `voter_adapters_broadcast_sainit` | One adapter per voter with the outcome reward, from the SA-RL step-300 merged weights. | `--task math --workflow voting_v2 --policy ip --scale 1.7B --control voter_adapters_broadcast_sainit` | `--paper-run d1fweqim` |
| `t1_length_weight` | Shared policy with each sequence's loss scaled by its role's mean response length. | `--task math --workflow voting --policy sp --scale 1.7B --control t1_length_weight` | `--paper-run s4hmrfca` |
| `t2_merged_minibatch` | Per-role adapters with one optimizer step per role per training step (mini-batch 192). | `--task math --workflow voting --policy ip --scale 1.7B --control t2_merged_minibatch` | `--paper-run c0zlpk56` |
| `kl_anchor_evaluator` | KL penalty to the base model on the evaluator adapter only (coefficient 0.01). | `--task math --workflow evaluator_optimizer --policy ip --scale 1.7B --control kl_anchor_evaluator` | `--paper-run akyv7jo2` |
| `cap_8192` | Continue an Eval-Opt run from a checkpoint with an 8192-token response cap. | `--task math --workflow evaluator_optimizer --policy ip --scale 1.7B --control cap_8192 --resume-from <ckpt>/global_step_320` | `--paper-run 6p4i9pm1` |
| `sp_extension` | Extend a shared-policy run to 450 steps (same experiment name, so it resumes). | `--task math --workflow voting --policy sp --scale 1.7B --control sp_extension` | `--paper-run nrg6etac` |
| `init_from_sa_adapters` | Initialize role adapters from given LoRA adapters (pass --init-adapter role=path). | `--task math --workflow voting --policy ip --scale 1.7B --control init_from_sa_adapters --init-adapter <role>=<adapter dir>` | — |

Notes on the controls:

- `voter_adapters_broadcast_sainit` starts from the SA-RL weights after 300 steps merged into the base
  model. Build them first:
  `python scripts/merge_lora_to_base.py --base_model Qwen/Qwen3-1.7B --adapter_path <SA-RL run>/global_step_300/actor/lora_adapter_generator --output_dir $MARL_INIT_WEIGHT_DIR/math/qwen3_1.7b_s300 --verify`
  (`MARL_INIT_WEIGHT_DIR` defaults to `checkpoints/init_weight`). Any cell accepts the same weights
  with `--base-model qwen3_<size>_s300`; the tag becomes part of the experiment name.
- `cap_8192` resumes the Eval-Opt IP 1.7B Math run from its step-320 checkpoint with a longer response
  cap; pass that checkpoint with `--resume-from`.
- `init_from_sa_adapters` loads trained LoRA adapters into the named roles before training. Under SP
  the `generator` adapter (or the first one given) initializes the shared adapter. For
  Orchestrator-Workers, an adapter given for `generator` initializes `worker`.
- `--processed-logprobs` (any cell) makes vLLM return processed log-probabilities, so that the logged
  per-role entropy-related statistics compare the trainer with the sampler at the same temperature. It
  is off in the paper's grid runs and on in two controls.

## 4. Evaluate checkpoints

Validation accuracy is measured off-policy on every saved checkpoint with the evaluator, which starts
a LoRA-enabled vLLM server and runs the same workflow classes:

```bash
# Math: the 1412-problem validation split, at the training length caps
python -m marl_workflows.eval.evaluate_checkpoints --task-type math \
    --checkpoints-dir checkpoints/rllm-workflow-MARL-v2 --experiment-filter '^voting-qwen3_1.7b-multi_lora-math$' \
    --dataset dapo_math --use-training-lengths --output-json eval_results.jsonl \
    --trajectory-output-dir evaluation_trajectories
# Code: the 1000-problem validation split
python -m marl_workflows.eval.evaluate_checkpoints --task-type deepcoder \
    --checkpoints-dir checkpoints/rllm-workflow-MARL-v2 --experiment-filter 'deepcoder' \
    --dataset deepcoder_primeintellect --use-training-lengths
```

- Always pass `--use-training-lengths`, so that evaluation uses the training prompt and response caps.
- By default every checkpoint whose step is a multiple of 10 is evaluated (`--eval-interval`);
  `--step-filter` and `--last-checkpoint-only` narrow it.
- Results are appended to `--output-json`, one JSON line per checkpoint; finished checkpoints are
  skipped when the job is re-run.
- Other modes (`--eval-mode base_model`, `single_agent_transfer`, `single_agent_generator_transfer`)
  evaluate the untrained workflows and the SA-RL adapter placed in a workflow.

On SLURM, wrap the same arguments:

```bash
python scripts/launch.py eval --slurm-config configs/slurm/dgxh_preempt_h100.conf --job-name eval-voting -- \
    --task-type math --checkpoints-dir checkpoints/rllm-workflow-MARL-v2 --dataset dapo_math --use-training-lengths
```

The in-training validation that the trainer logs (`test_freq`) runs on AIME 2025 (30 problems) for Math
and is a progress signal only; report accuracy from the evaluator.
